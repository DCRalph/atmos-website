Contract data: artist details and hire fields

The contract generator fills about half of each contract from the database. The rest is typed every time and is gone when the tab closes. This is where that data could live, with a recommendation for each decision.

1 · Where artist details live

Legal name, contact email, phone, address, GST number and bank account. None of it may ever reach a public page, and it has to work for artists who have not claimed their profile.

A · Columns on the artist profile

Add the fields straight onto ArtistProfile.

For

  • One table, one admin form.
  • Smallest migration.

Against

  • Leak risk. The profile is read in 35 places on the server, four of them take the whole row, and several are public.
  • Every future query has to remember to leave the private columns out.

B · A separate private details table Recommended

One row per artist, joined only by the admin contract reader and the artist's own dashboard.

/// Never selected by a public procedure.
model ArtistPrivateDetails {
  artistProfileId   String   @id
  legalName         String?
  contactEmail      String?
  phone             String?
  address           String?
  gstNumber         String?
  bankAccountName   String?
  /// Encrypted at rest, the way stored reports already are.
  bankAccountNumber String?
  updatedAt         DateTime @updatedAt
  updatedById       String?

  artistProfile ArtistProfile @relation(fields: [artistProfileId], references: [id], onDelete: Cascade)
}

For

  • Private by default. Nothing sees it unless it asks for it by name.
  • Works for unclaimed profiles.
  • Additive: no existing query or page changes.

Against

  • One more join in the contract reader.
  • A second form section to build.

C · On the user account

Store the details against the login that claimed the profile.

For

  • The artist owns and edits their own data.

Against

  • Unclaimed profiles have no account, so most of a line-up would still be typed by hand.
  • Mixes artist paperwork into the auth table.

Who types it in

These stack. Each one writes to the same table.

  1. Admin, on the artist sheet Start hereA Private details block under the existing profile fields. Admins only.
  2. The artist, in their dashboardClaimed artists keep their own details current. The bank number shows masked after saving.
  3. A one-time linkEmail an unclaimed artist a form, the way rental decisions and photo signups already use a token link. Build only if chasing details becomes a chore.

2 · Where booking terms live

Fee, whether it includes GST, guest list places and extras belong to one artist in one set, not to the artist.

A · Columns on the booking Recommended

The line-up already has a row for each artist in each set. A back to back gets a fee per artist for free.

model GigSetArtist {
  // existing columns
  feeCents        Int?
  feeIncludesGst  Boolean?
  guestListPlaces Int?
  contractNotes   String?
}

For

  • Edited once, on the Contracts page or the run sheet row.
  • Fees become data: a gig's artist costs can be totalled and fed to event profit later.
  • Integer cents, matching ticketing.

Against

  • Fees sit on a table the public line-up reads, so the public line-up query must keep selecting named columns. It already does.

B · A usual fee on the artist, overridden per booking

Adds usualFeeCents to private details so a new booking starts with a number. Worth adding to A only once the same artists are booked often.

C · Keep typing it

No schema change. The fee is retyped each time the contract is opened and nothing records what was agreed.

3 · Filling the rest of the hire contract

The blank hire fields come from three different places, so they need three small changes, not one.

Gear catalogue: replacement value and serials

model GearItem {
  // existing columns
  replacementValueCents Int?
  serialNumbers         String[]
}
  • Replacement value is entered once per item and printed on every contract. Clause 5.1 charges it when gear is lost, so it should not depend on someone remembering the number.
  • Serials as a list on the item Recommended matches how gear is counted today, as a quantity on hand. The contract prints the list and the ones going out are circled at handover.
  • A row per physical unit is the alternative: it records which unit went out and its condition history. A bigger build that changes how availability is counted. Worth it only if damage disputes come up.

The rental: who, where and the bond

A · Real columns, saved from the contract page Recommended

The contract page gets a Save button that writes what was typed back to the rental, so the next open is already filled.

model Rental {
  // existing columns
  phone          String?
  organisation   String?
  address        String?
  useLocation    String?
  collectionTime String?  // "4:00 pm"
  returnTime     String?
  bondCents      Int?
}

For

  • Typed, searchable, reportable: bonds held can be listed.
  • Phone and location can be asked in the booking wizard, two extra fields.

Against

  • A new contract field means a new column.

B · One JSON column of overrides

Rental.contractFields Json holds whatever was typed into any field.

For

  • No schema change when the contract gains a field.
  • Any field can be overridden, including ones that came from the database.

Against

  • Untyped and not queryable.
  • Nothing else in the admin can use the phone number or the bond.

C · Admin-defined extra fields

A settings page where extra labelled fields are added to every hire contract, for example vehicle registration.

For

  • New fields without a deploy.

Against

  • The most to build, and the contract layout has to cope with any number of fields.
  • Only pays off if the fields change often.

Defaults in settings

The settings store already exists. A handful of keys cover what is the same on every contract.

SettingUsed for
Legal entity and NZBNThe parties line on both contracts, which says only "Atmos Media" today

  • Not in settings: the numbers inside the terms (30 minutes, 14 days, 50%, 48 hours). They stay in code so a change to what people sign is reviewed.

4 · Saved contracts

Optional, and a step beyond the question. Sections 1 to 3 make the contract fill itself. This records what was actually issued.

model Contract {
  id           String         @id @default(cuid())
  kind         ContractKind   // PERFORMER | HIRE
  setArtistId  String?
  rentalId     String?
  /// Every field exactly as it was printed.
  fields       Json
  termsVersion String
  status       ContractStatus // DRAFT | SENT | SIGNED
  signedFileId String?        // the signed copy, uploaded
  createdById  String
  createdAt    DateTime       @default(now())
}

For

  • A record of what was agreed, even after a set time or fee changes.
  • The Contracts page can show who has signed and who has not.
  • The base for sending a link to sign online later.

Against

  • The largest piece here.
  • Not needed while contracts are printed, signed and filed by hand.

Suggested rollout

  1. Artist private details and the gear catalogueThe private details table with its admin form, plus replacement value and serials on gear items. Both additive, and nothing public changes. Contracts start filling legal name, phone, GST, bank and the two gear columns.
  2. Booking terms and rental fieldsFee, GST and guest list on the booking. Phone, organisation, address, location, times and bond on the rental, with Save on the contract page. Legal entity and default bond in settings.
  3. Self-serve and saved contractsArtists edit their own details in the dashboard. Contracts are saved with a status. Only if the first two prove worth it.

Open questions

  • Encrypt bank account numbers? Recommended. An encryption helper already exists for stored reports, and it keeps numbers out of database backups in plain text.
  • Store photo ID numbers? Recommended not to. Type it on the contract at handover and keep it on paper, or store only "ID sighted".
  • Privacy policy. It needs a paragraph on performer and hirer details before any of this is collected, with the same seven year retention as order records.
  • Legal entity. The contracts still name only "Atmos Media". The company name and NZBN are needed for the settings in step 2.
  • Withholding tax. If performer fees are schedular payments, private details also needs an IRD number and tax rate. Confirm with the accountant before step 1 so the table is built once.
