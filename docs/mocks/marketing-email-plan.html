Marketing email

Send emails to one or more lists through Resend, with working unsubscribe, bounce handling, and results per send. Our database stays the list. Resend only delivers. Phase 1 is safe to ship before anything sends, because it is the part that lets people leave.

What exists today

  • One flat list. newsletter_subscription is an email plus a removed flag. No name, no source, no list.
  • Three ways in. The newsletter form (home and gig pages), the gig photo signup (joins the newsletter, the page says so), and the checkout box (marketingOptIn, express consent per UEMA).
  • Nothing sends to it yet, and there is no unsubscribe link anywhere. Only admins can flip removed.
  • Resend plumbing is there. sendEmailBatch sends 100 per call with an idempotency key, and the inbound-email route already verifies Resend webhooks with resend.webhooks.verify. Batch sends accept headers and tags, which is all we need.
  • Two traps. "Campaign" is taken (tagged links and spend), so these are mailouts. And vercel.json caches /email/* as immutable for a year, so the unsubscribe page must not live there.

Approach

Resend now has Broadcasts, Segments and Topics, which would give us a hosted editor and unsubscribe page. The catch is two copies of every list.

Recommended

Our DB is the list, Resend is the pipe

Lists, people, consent and unsubscribes live in Postgres next to the signups that create them. We render the email, send through the batch API, and read delivery events back by webhook.

Signup paths, account deletion and imports touch one table. Ticket results join on the same database. We write the queue and the unsubscribe page, roughly a few hundred lines.

Resend Broadcasts

Sync every subscriber into Resend Segments, write in Resend's editor, send from their dashboard. Unsubscribe page and stats come free.

Every signup, removal and deletion has to be mirrored there, and unsubscribes made on their page have to be mirrored back by webhook. Two sources of truth for consent is the thing most likely to email someone who left.

Data

Five models replace NewsletterSubscription. The migration copies every row into Newsletter, and removed rows come across as unsubscribed on their updatedAt.

model MailingList {
  id          String    @id @default(cuid())
  slug        String    @unique  // "newsletter"
  name        String             // shown on the preferences page
  description String?
  public      Boolean   @default(true)
  archivedAt  DateTime?
  members     ListMembership[]
}

model Subscriber {
  id              String    @id @default(cuid())
  email           String    @unique  // lowercased, trimmed
  name            String?
  /// Hard bounce, complaint or Resend suppression. Never sent marketing while set.
  suppressedAt    DateTime?
  suppressedWhy   SuppressionReason?   // BOUNCED | COMPLAINED | RESEND
  createdAt       DateTime  @default(now())
  memberships     ListMembership[]
  received        MailoutRecipient[]
}

model ListMembership {
  subscriberId    String
  listId          String
  /// "newsletter-form", "checkout:<eventId>", "photo-signup:<gigId>", "import", "admin:<userId>"
  source          String
  subscribedAt    DateTime  @default(now())
  /// Null while subscribed.
  unsubscribedAt  DateTime?
  unsubscribedVia UnsubscribeVia?      // ONE_CLICK | PAGE | COMPLAINT | ADMIN
  /// The mailout whose link they used, for "unsubscribes caused".
  unsubscribedFromMailoutId String?
  @@id([subscriberId, listId])
}

model Mailout {
  id           String        @id @default(cuid())
  slug         String        @unique  // utm_campaign
  subject      String
  previewText  String?
  body         Json                    // Lexical state
  html         String?       @db.Text  // frozen at send, without per-person links
  text         String?       @db.Text
  status       MailoutStatus           // DRAFT | SCHEDULED | SENDING | SENT | CANCELLED
  scheduledFor DateTime?
  startedAt    DateTime?
  finishedAt   DateTime?
  lists        MailingList[]           // who it went to
  recipients   MailoutRecipient[]
  createdById  String?
}

model MailoutRecipient {
  id           String     @id @default(cuid())
  mailoutId    String
  subscriberId String
  email        String                  // as it was when sent
  status       RecipientStatus         // QUEUED | SENT | FAILED | SKIPPED
  attempts     Int        @default(0)
  error        String?
  resendId     String?    @unique
  sentAt       DateTime?
  deliveredAt  DateTime?
  bouncedAt    DateTime?
  complainedAt DateTime?
  clickedAt    DateTime?
  openedAt     DateTime?
  @@unique([mailoutId, subscriberId])   // one email per person per mailout
  @@index([mailoutId, status])
}
  • Migration SQL goes in prisma/manual and is applied to prod by hand before the PR, as usual. The old table is dropped in a follow-up once nothing reads it.
  • Scheduled times are compared with now() in SQL, not in JS, so node-pg's local-time reading of timestamps cannot fire a mailout 13 hours early.

Sending

  1. Commit. Pressing Send (or the scheduled time arriving) renders the body once into the Atmos layout, stores the HTML and text, and snapshots recipients in one INSERT … SELECT DISTINCT: subscribed members of the chosen lists, not suppressed. Status becomes SENDING.
  2. Drain. drainMailouts() runs straight away through after(), and from a new /api/cron/mailouts every minute. It claims 100 queued rows with FOR UPDATE SKIP LOCKED, so the cron and the first run never send the same row twice.
  3. Recheck. Rows whose person unsubscribed or got suppressed since the snapshot are marked SKIPPED.
  4. Send. One sendEmailBatch call per 100, each email with its own unsubscribe link and headers, tags mailout_id and recipient_id, and an idempotency key built from the mailout and first recipient id. A crash and retry inside 24 hours is a no-op at Resend.
  5. Pace. Calls are spaced to Resend's rate limit (2 per second by default, so about 12,000 emails a minute). The run stops before the function's time limit and the next cron tick carries on.
  6. Fail. A failed batch bumps attempts and goes back in the queue. After 3 it is FAILED with Resend's error, and "Retry failed" re-queues them.
  7. Finish. When nothing is queued, status becomes SENT. Cancel flips status to CANCELLED, and the remaining rows to SKIPPED.

Unsubscribe

  • Token. HMAC of subscriber id and mailout id with a server secret, the same idea as ticket access tokens. Nothing stored, never expires, cannot be guessed or edited to another person.
  • Footer link goes to /unsubscribe/<token>. Loading the page changes nothing (link scanners in work inboxes open every link). It shows their public lists with toggles, an "Unsubscribe from everything" button, and resubscribe if they change their mind.
  • One-click header posts to /api/unsubscribe/<token>, per RFC 8058. That removes them from the lists the mailout went to, with no page.
  • Complaint (marked as spam) unsubscribes them from everything and suppresses them.

Rules we must meet

  • NZ Unsolicited Electronic Messages Act 2007. Consent before sending (we record source and time per list), accurate sender details with a way to contact us, and a working unsubscribe honoured within 5 working days that keeps working for at least 30 days after the send. Ours is instant and permanent.
  • Gmail and Yahoo bulk sender rules. SPF, DKIM and DMARC on the sending domain, one-click unsubscribe headers, and spam complaints kept under 0.3%. Suppressing complainers immediately is what keeps that rate down.
  • Buying a ticket is not consent. Only the checkout box adds a buyer to a list, as now.

Decisions for you

  1. Which lists to start with?Newsletter is seeded from the current table. Anything else (by city, by genre, crew, artists) is a two-second create in the admin, but it changes what the signup forms offer.
  2. A sending subdomain, like news.atmosmedia.co.nz?Recommended. Needs DNS records added in Resend. It keeps marketing complaints from dragging down ticket email delivery.
  3. Open and click tracking in Resend?Recommend clicks only, or neither. UTM tags already measure the clicks that matter (ticket sales), opens are unreliable since Apple Mail, and Resend's click tracking rewrites every link through their domain.
  4. Double opt-in (confirm by email before joining)?Recommend no. UEMA does not need it, BotID already guards the forms, and it loses a share of real signups. Easy to add later.
  5. What goes in the footer as our sender details?Business name, a contact email, and ideally a postal address or city.
  6. Does the Resend plan cover the volume?Mailouts go through the sending API, so they count against the same monthly email quota as tickets. Worth checking before the first big send.
  7. Admins only, or event organisers too?Recommend admins only to start. Sending to the whole list is the one action here that cannot be undone.
