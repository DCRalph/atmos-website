Paste a link, get a gig

An admin pastes an Instagram post or reel, the caption and image are read, and a gig comes back filled in. Nothing is public until it is checked. Everything the import guessed can be overridden, and every filled field says where it came from.

All three directions share the same pieces: a source panel showing the post, prefilled fields carrying provenance, artist handles matched against creator profiles, the post image cropped to the 3:4 poster, and a draft that has to be published deliberately.

They differ in where the work happens. A is a guided route of its own. B is one dense screen with the post beside the form. C keeps the existing gig editor and treats import as a way to fill it.

Worth knowing before we build. Instagram will only hand over captions and media for accounts we own, through the Graph API. An @atmos.nz post imports cleanly. A venue or promoter post does not, so every direction keeps a manual path: paste the caption, drop the image in, and the same extraction runs on it.

What gets extracted

  • Title and venue
  • Start and end time, resolved to a real date in Pacific/Auckland
  • Short description and long description
  • Ticket link, including link-in-bio text
  • Line-up as run sheet SET rows, back to backs kept as one slot
  • Tags matched to existing gig tags only
  • Poster from the post image, cropped to 3:4

A. Stepped wizard

Import gets its own route at /admin/gigs/import. Four steps: source, review, line-up and poster, publish. Each step is finished before the next one appears, and the gig only exists as a draft from step two onwards.

Easiest to get right the first time and the safest for someone who imports occasionally. It is also the most clicks, and the run sheet and poster are seen apart from the fields they belong with.

B. Split review

One screen. The post is pinned on the left and the whole gig form is on the right, already filled. No steps, no next button. Scroll down the form, fix what is wrong, publish from the bar at the top.

Fastest for someone importing several gigs in a sitting, and the only direction where you can see the caption while editing the run sheet. Dense, and it wants a wide screen to be comfortable.

C. Import into the editor you already have

No new page. Import is a dialog on the gigs list, and it drops its values straight into the existing gig editor. Every field the import filled is marked and can be undone one at a time. The gig is a draft until the publish switch is thrown.

By far the least new surface, and an imported gig is edited with the exact controls as any other. The post is behind a link rather than beside the form, so checking the extraction against the caption is slower.

Drafts, whichever direction wins

A gig gains a status. Draft gigs are invisible on the site, in the home page selection, in search, and in the mobile app. They still show in the admin list, filed under their own tab, so a half finished import cannot be lost or accidentally shipped.

This is the piece that has to exist first. Import writes drafts; everything else about it is presentation.

What has to change underneath

Same for all three directions. The only part that differs between them is which screens read it.

Draft status on a gig

  • status on Gig, DRAFT or PUBLISHED, defaulting to PUBLISHED so nothing already in the database disappears.
  • Every public read filters to published: the gigs pages, home placements, featured and past lists, sitemap, and the mobile feed. This is the part worth being thorough about.
  • A published gig can be pulled back to draft. Useful beyond import.

A record of the import

  • GigImport holds the source URL, the raw payload Instagram returned, the structured extraction, and which gig it produced.
  • Keeping the extraction is what lets a field say where it came from and offer a revert, long after the import.
  • Re-reading the same post updates the record rather than making a second gig.

Reading the post

  • Instagram Graph API for Atmos owned media. Caption, media URL, permalink and timestamp come back directly.
  • Anything else needs the caption pasted and the image dropped in. The same extraction runs either way, so this is a smaller branch than it sounds.
  • Carousels give several images. The first is the poster, the rest are offered.

Caption to fields

  • One Claude call returning a schema-validated object. Each field carries the caption substring it came from and a confidence, so provenance is data rather than a guess made in the UI.
  • Dates resolve in Pacific/Auckland against the post date, which is how "Friday 23 October" becomes a real timestamp.
  • Tags only ever match existing gig tags. Import never invents one.
  • Handles are looked up against creator profiles. No match means a name on the run sheet, never a silent new profile.
Two calls worth making before I build. First, whether import should ever create a creator profile on its own, or always stop and ask. Second, whether a draft gig should be reachable by direct URL for sharing a preview, or be fully invisible until published.
